You can't improve workspace agents you can't measure

July 3, 2026 · WorkspaceBench

This project started with a question I kept coming back to at OpenBB: if agents are going to work inside financial workspaces, how do we know they are actually useful? Not useful in a demo. Useful in the boring, concrete way that matters: can they inspect data, call tools, build dashboards, repair broken state, and leave something behind that a human can open the next morning?

I could not answer that question, because nothing measured it. So I built WorkspaceBench. It includes the harness, a deterministic workspace simulator, 300 scenarios, the graders, and every number in this post.

This post covers the benchmark end to end: how a workspace task becomes a scored episode, how the scenarios are generated and certified, and what real models score.

01 · Why a benchmark

Two ideas carry this section: agent work should be graded like software, and a workspace agent's answer is the state it leaves behind.

The pattern, elsewhere

An eval bench is a repeatable test suite for agents. Instead of saying "this model feels better", you give every agent the same task, the same tools, the same starting state, and the same grader.

The inspiration is the pattern. SWE-bench (Jimenez et al., 2023) made software issues measurable. Terminal-Bench made terminal work measurable. WebArena (Zhou et al., 2023) and OSWorld (Xie et al., 2024) pushed the same idea toward browser and desktop tasks. WorkspaceBench is my attempt to bring that discipline to financial workspaces.

A chat answer is not enough

Most agent demos are still judged by whether the final answer sounds good. That is fine for conversation and weak for real workflows. In a workspace, the important question is not what the agent says. It is what the agent changed.

Did it create the correct widget? Did it use the right ticker? Did it inspect the schema before creating anything? Did it repair the dashboard without breaking the layout? A software agent is judged by whether the tests pass, not by how confident the diff description sounds. A workspace agent should be judged the same way: by the dashboard, tabs, widgets, layout, and notes it leaves behind.

So WorkspaceBench grades final state deterministically — exact widget identifiers, exact data arguments, layout bounds, overlap checks — before it considers anything the agent said, the same final-state-first stance τ-bench takes for tool agents. One thing worth being precise about:

WorkspaceBench measures whether an agent can operate the workspace, not whether it can reason about markets.

The fixture data is deterministic and fake on purpose. The finance framing lives in the task language — mapping "prep the earnings review" onto the right widgets is a workspace skill — but no scenario is graded on investment insight. That keeps the reward signal clean, and it is also what lets the same grader later serve as a training reward.

That clean reward has an obvious edge case: content checks are deterministic fact-presence checks, so a note passes when it mentions the required ticker, EPS, or revenue. A keyword-stuffing agent could game that layer. I accept that tradeoff deliberately: no LLM judge variance, a clean training reward, and trace checks such as schema-before-create, invalid-call budgets, and missing_tool_result requiring the agent to read the data it cites close the cheapest stuffing paths. Reward robustness gets stress-tested the day the grader becomes an RL reward; the trace checks are the first line of defense for that, too.

02 · Inside the benchmark

How a task becomes a score: the loop, the surface the agent lives on, the kinds of work, and the contracts that hold it together.

From workflow to scored episode

The core loop is deliberately small. A scenario defines the task. The harness seeds a deterministic workspace from fixture backends. The agent emits tool calls. The simulator applies them. The grader checks the final state and the trace.

The simulator is intentional. It is not a pixel or browser simulator — it is a deterministic state machine for the Workspace MCP contract (src/workspace_bench/workspace/simulated_workspace.py). That makes runs fast, reproducible, and cheap enough for CI. A live smoke runner (src/workspace_bench/workspace/live_mcp.py) drives the same scenario contract through a real local workspace-mcp sidecar and websocket bridge, with the benchmark simulator acting as the browser side. A separate read-only audit lists the hosted deployment's tools, prompts, and resources and diffs that surface against what the scenarios assume.

The MCP surface: tools, prompts, resources

The agent's world is exactly what the Workspace MCP server exposes: 20 tools, 2 prompts (the server's own usage guidance and session context, fetched with get_workspace_prompt), and MCP resources (the app-builder index and the workspace skills, read with read_workspace_resource). A benchmark that skips the prompts and resources isn't measuring workspace competence — an agent that ignores the app-builder index rebuilds by hand a dashboard the platform would have assembled for it.

Every row below is live from the benchmark data: how many of the 300 scenarios exercise each part of the surface. Click one for what it does, example tests, and footage of it firing in the real Workspace.

Five kinds of workspace work

Scenarios are grouped into five workflow levels, each mapping to something an analyst actually does. Levels classify the kind of work — they are not the difficulty axis; that is the tier's job, later. The distribution is deliberate — dashboard construction (L2), the most product-relevant slice, is a quarter of the suite.

03 · A designed distribution

The 300 scenarios are not a collection; they are a lattice — and the difficulty axis had to earn its shape empirically before any result below could be trusted.

Generated, not hand-written

Every scenario in the benchmark is generated — including the early ones I drafted myself, which were AI-written too, so pretending they were a special hand-audited caste would be dishonest. What matters is not who typed the JSON; it is whether the distribution is designed. My first pack quietly skewed: four MCP tools appeared in exactly one scenario each, and half the suite tested the same single-widget motion. The lesson from TMax — 14,600 terminal environments sampled compositionally from nine structured axes — is that a task distribution should be a designed property, not an accident of what the author felt like writing.

So the suite is generated compositionally: 15 families, each anchored on one MCP capability, each carrying a complete t0–t4 ladder — 4 scenarios per rung per family, 300 total. The same tool is tested at every difficulty. delete_widget at t0 means "remove the only widget"; at t4 it means "remove one duplicate, fix the survivor, document the repair" in a single episode. Tiers are not the L0–L4 levels from earlier — levels classify the kind of work, tiers grade how structurally demanding the episode is, and a single-widget L1 task can sit anywhere from t0 to t4.

Tiers are structural, not adjectives. A tier is defined by what the task is made of — composition, seeded pathologies, discovery pressure, turn budget — and difficulty labels derive from the tier (the boundary tiers t1 and t3 straddle two bands, as boundaries should). The composition is measurable: the average episode uses 2.3 tools at t0 and 5.0 at t4.

The shape of the suite

The question I actually care about — and the one a flat scenario count hides — is which tools each test requires, and how that grows with tier. One row per test; an x marks each tool the reference solution uses; the family's anchor tool is inverted. Click any test to see its prompt, its reference tool sequence, and the exact checks the grader runs.

Split discipline is built in, and it is sampled, not blessed: 180 train / 60 validation / 60 test, stratified per family×tier cell so every slice of the distribution appears in every split. No scenario is more equal than another. One honest caveat for anyone training on this: stratification means the same template family spans splits with different parameters — for evaluation that is exactly right, but if you train on the train split, prefer held-out-family splits to rule out template-shaped shortcuts. All 300 scenarios ship publicly, including the test split, so the split is a bookkeeping device, not contamination protection. The real defense is that the generator is deterministic and template-driven, so fresh held-out packs can be regenerated at will. Reproduce or extend it: 

# regenerate the pack (deterministic templates, no LLM required)
python scripts/generate_gen_pack.py

# certify: oracle passes, no-op fails, quotas + fingerprints hold
uv run --extra dev workspace-bench validate \
  --pack all --min-scenarios 300

# rebuild the per-test tool matrix
python scripts/generate_tool_matrix.py

Mostly contracts

The repo works because every layer speaks a simple shape. Scenarios are JSON. Agent actions are JSONL tool calls. Results are graded scorecards with stable issue codes. The harness writes a task envelope, sets four environment variables, runs your agent command, reads its tool calls, and grades what happened. Your agent never has to import the package.

Calibration caught our own bugs

Before trusting any of the numbers below, the tiers had to earn them. The protocol: run a mid-strength gating model (gpt-4.1-mini) over all 300 scenarios and check that measured pass rates fall monotonically from t0 to t4 — if difficulty is structural, the curve must show it.

The first gating run did something better than confirm the ladder: it exposed three defects in our own benchmark. Two brand-new families scored 0/20 — because the harness never documented the two new tools' schemas to models (they invented argument shapes), and because several prompts demanded facts the grader checked but the instructions never requested. A third pass caught an inconsistency in when schema-discipline was instructed versus silently expected. All three were fixed at the generator level, the pack re-certified (oracle 300/300, no-op 0/300), and the sweep re-run from scratch.

The before/after tells the story: the gating curve went from 83–67–48–47–30 (with two broken families and a suspicious t2/t3 tie) to 98–92–77–52–33 — monotonic, well-spaced, t0 nearly-free, t4 unfloored. That loop — design structurally, certify, calibrate empirically, let calibration expose your own bugs, fix, recalibrate — is the discipline this whole series argues for. It cost about three days of compute babysitting, and it is the difference between a benchmark and a demo.

04 · Results

The first useful question is not whether one model produced a nice answer once. It is whether different agents can solve the same workflows under the same constraints, and whether their failures are understandable.

These are real runs from the interactive comparison harness (src/workspace_bench/reports/model_compare.py): each model chooses one tool call, receives the simulated workspace result, then chooses the next call — all 6 models against the same 300 certified scenarios, same grader, same logs. Two run locally through Ollama for free; the rest go through vendor APIs and OpenRouter. Every episode's full transcript is exported as portable rollout JSONL in runs/exports/.

The board

Two things to read off the table before the charts. First, the spread: 94.0% to 49.7% strict separates roughly two generations of capability, and the ordering is stable — across all 300 scenarios there is exactly 1 inversion between the top and the bottom of the board (a t0 delegation task GPT-5.5 fumbles and Qwen3 8B happens to pass). All results are single-attempt pass@1 from one run (GPT-5.5 additionally samples at temperature 1), so per-cell numbers carry sampling noise; the harness supports --repeats and pass@k for anyone who wants error bars. Second, the gap between mean check score and strict pass: GPT-5.5 earns 99.2% of all grader checks but passes 94.0% of scenarios — partial credit flatters everyone, which is exactly why the headline metric is all-checks-or-nothing. One inversion hides in the mean checks too: GLM-5.2's mean check score (90.1%) sits below gpt-4.1-mini's (95.7%) and even Qwen3 8B's (90.8%) despite a far higher strict pass rate — GLM fails messily across many checks while weaker models fail narrowly. The family block at the bottom is the benchmark's diagnostic panel: read down a column and you get a model's failure fingerprint; read across the inspect row and you see the suite's open problem.

Adapter plumbing can cost a frontier model double-digit points. OpenRouter can route Anthropic models through Bedrock, and requesting json_schema response_format there degraded Sonnet to schema-minimal outputs; a controlled A/B diagnosed it, and the harness fixed the adapter by disabling response_format on that route.

Model by model

The distribution shows three distinct ladder shapes, and each one is informative. GPT-5.5 compresses the ladder: 95% at t4, barely below its t0 — multi-intent composition is essentially solved for it, and its residue is precision and ambiguity. Claude Sonnet 5, gpt-4.1-mini, and gpt-oss:20b degrade monotonically, each an echo of the gating curve at a different altitude — the tier axis measures the same thing at every capability level. Qwen3 8B shows the third shape: near-parity with the mid-field at t0–t1, then a cliff — it halves at t2 and lands at 17% by t4. Small models don't degrade on this benchmark; they break, and they break exactly where episodes become multi-step. The agreement panel makes the same point from the other side: unanimity falls from 36/60 at t0 to 6/60 at t4, so the contested band — 192 of 300 scenarios — is concentrated precisely where the ladder claims difficulty lives (24, 26, 43, 45, 54 contested scenarios across t0→t4).

Who passed what

The rows nobody passes are the most valuable output of the whole sweep. 15 of 300 scenarios defeat all six models, and they are not scattered: 8 are inspect-family tasks (deduplicate or reconcile a workspace the agent did not build — ambient-state reasoning), 4 are companion-widget parameter tasks, 2 are precise layout splits, and 1 is a full skills-driven tearsheet. Even GPT-5.5 passes only 11/20 of the inspect family. That list is simultaneously t5's seed, a ranked work queue for the tool surface itself, and the strongest evidence that the remaining headroom is about reading state, not composing calls. At the opposite end, 93 scenarios are passed by everyone — the sanity floor, 70 of them in t0–t1, which is what "t0 nearly free" should look like.

Failures are also model-specific in ways a single number hides. Qwen3 8B scores 4/20 on the apps family — long instantiation chains — where every other model scores 17 or better. GLM-5.2 is the only model that struggles with the prompts family (8/20), because it skips the prompt fetch it considers unnecessary. gpt-oss:20b bottoms out on documentation notes (5/20). Six models, six different failure fingerprints on identical tasks — which is why the issue-code explorer below follows whichever model you pick, instead of averaging the differences away.

The honest read: the benchmark separates the mid-field sharply, but the frontier is already near the ceiling — and what it still fails is precision and ambient state, not composition. That is the roadmap for t5.

Don't take my word for any of this. Every chart above is one command away, and each run writes analysis.md, chart.png, and full per-scenario traces:

# run any adapter file against the full 300-scenario release
uv run --extra dev workspace-bench compare-models \
  --models-file models.json --pack all --difficulty all

# re-certify the pack before trusting anything (oracle 300/300, noop 0/300)
uv run --extra dev workspace-bench validate --pack all --min-scenarios 300

# export a finished run as portable rollout JSONL
uv run --extra dev workspace-bench export-rollouts \
  --comparison-dir runs/comparison/<run> --output rollouts.jsonl

Failures get names, not vibes

Every failed check maps to a stable issue code (all of them defined in src/workspace_bench/core/graders.py), and issue codes aggregate across a run. That turns "model X is worse" into something specific: the gating model's #1 failure is schema-before-create discipline, GLM-5.2 burns attempts on invalid calls, and GPT-5.5's residue is exact-layout precision. Same benchmark, different failure fingerprints — that specificity is the point.

The difference between a useless and a useful failure message:

bad  "The model did not complete the task."
good missing_widget: Expected one Bench Equities/price_performance
      widget with data_args {"symbol": "AAPL"}, found zero.

05 · The score cuts both ways

This post is only about the eval. But look at the failure taxonomy again: GLM-5.2 made 303 rejected tool calls across its 300-scenario run, enough to fail the invalid-call budget on 45 scenarios. That is not only a verdict on the model. It is a verdict on the tool surface — the schemas, the names, the error messages the workspace hands to agents.

The natural next move is to flip the benchmark around: fix the model, vary the tools, and use the same graded runs to optimize the Workspace MCP server itself. And once the tool surface is stable, the traces those runs leave behind become training data worth keeping. Both of those are stories for another day.

Incentives always win. The least I can do is measure the ones I am creating.
