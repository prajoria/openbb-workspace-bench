The benchmark grades your API, not just the agent

Part 1 measured agents operating OpenBB Workspace. But read the failure taxonomy again and half of it isn't about the models at all. When a capable model burns dozens of attempts on malformed calls, invented ids, and skipped schema lookups, that is a verdict on the tool surface — the schemas, names, and error messages the workspace hands to agents. Part 2 flips the harness around: fix the model, vary the tools, and optimize the MCP server with the same graded runs.

The evidence

Failures are API bug reports.

This is the issue-code distribution from Part 1's core run: gpt-oss:20b, 25 scenarios, 3 attempts each, 75 graded episodes. In Part 1 we read it as a model report card. Read each code again with a product hat on and it becomes a queue of MCP-surface bugs, ranked by frequency.

The point is not that the model is blameless — a frontier model avoids most of these traps, which is why GPT-4.1 passes 98.7% of the same tasks. The point is that traps is the right word. An MCP surface that only frontier models can operate reliably is leaving most of the market's agents behind, including the cheaper models enterprises actually want to run.

API diagnosis

The model reading blames the agent. The API reading asks what the tool surface could have done to prevent the failure class entirely.

Why this framing matters: models improve on their vendors' schedule. The tool surface improves on yours. Every failure class you eliminate at the API level is a gain that applies to every agent, every model tier, on day one.

The method

Fix the model, vary the tools.

Normal benchmarking holds the tasks constant and swaps models. This is the mirror image: hold the model constant, change one thing about the tool surface, rerun the same 25 scenarios × 3 repeats, and diff the issue codes. The benchmark's determinism is what makes this a controlled experiment instead of an anecdote.

Three experiments, each targeting the top of the failure distribution. Baselines are from the Part 1 run; the changed arm reruns after the simulator's tool surface is modified — and any fix that survives ships to the real workspace-mcp server, with smoke-workspace-mcp --check-surface keeping the two in sync.

Protocol, stated up front: same model (gpt-oss:20b, with GPT-4.1 as the saturation control), same 25 scenarios, 3 repeats per arm, one tool-surface change at a time. Success is a drop in the targeted issue class without regressions elsewhere — and the grader's trace checks stay unchanged, so agents can't pass by gaming softer rules. Results will replace these badges when the runs land.

Making it permanent

CI for the tool surface.

One-off experiments decay. The durable version is a regression loop: every change to the MCP server's tools, schemas, or descriptions runs the benchmark with pinned models before it ships. Pass rates and issue-code counts become the release gate — the same way a test suite gates a code change.

The regression loop Click a stage

Change

A tool-surface change is anything an agent can observe: a renamed argument, a reworded description, a new error payload, a scoped response. Each is a product decision that today ships unmeasured.

Where this goes next

Stabilize the interface, then farm it.

There is a second reason to run these experiments before anything else: training data. Every trace collected against a tool surface you are still changing bakes in workarounds for flaws you intend to fix — and describes an API that will no longer exist. Optimize the tools first, and the traces that come after are worth keeping.

Part 3 starts there: turning graded traces into SFT data, preference pairs, and a step-based learning environment.
