The benchmark grades your API, not just the agent

July 2026 · Part 2 of 3 · WorkspaceBench · Part 1 · Part 3

Part 1 ran six models against 300 certified scenarios and read the results as a verdict on the agents. This post reads the same results the other way. When a capable model burns attempts on malformed calls, invents argument shapes, or skips a schema lookup it was never told mattered, that is not only a model failure — it is a verdict on the tool surface: the schemas, the names, the error messages, and the documentation the workspace hands to agents.

The asymmetry is why this reading matters. Models improve on their vendors' schedule. The tool surface improves on ours. Every failure class eliminated at the API level is a gain that applies to every agent, at every capability tier, on day one.

Two accidental experiments

The strongest evidence in this post was not designed. It happened to us during Part 1's calibration, and both incidents are controlled experiments in exactly the sense this post cares about: same model, same scenarios, same grader — one surface variable changed.

Failure fingerprints are surface signals

Part 1 showed each model failing differently on identical tasks. Read those fingerprints as bug reports against the surface, and each one names a concrete API change — that mapping is the experiment queue for this post.

The method: fix the model, vary the tools

Normal benchmarking holds tasks constant and swaps models. This is the mirror image: hold the model constant, change one thing about the tool surface, rerun all 300 scenarios, and diff the issue codes. The benchmark's determinism is what turns this from anecdote into controlled experiment, and Part 1's calibration gives the two instruments the protocol needs: gpt-4.1-mini as the sensitive mid-strength probe (strict 211/300 — plenty of headroom in both directions), and GPT-5.5 as the saturation control (94% — any fix that drops it is a regression, not an improvement).

Success criterion, stated before any run: the targeted issue class drops for the probe model without regressions elsewhere, and the grader's checks stay byte-identical — agents must not pass because the rules got softer, only because the surface got clearer.

The experiments

Four changes, one at a time, each targeting a fingerprint from the table above. The before/after payloads are concrete; the result badges are honest — these runs land after the surface changes are implemented in the simulator, and any fix that survives ships to the real workspace-mcp server with smoke-workspace-mcp --check-surface keeping the two in sync.

Making it permanent

One-off experiments decay; the loop is the product. Every surface change reruns the same release gates from Part 1 — oracle 300/300, no-op 0/300, quota and fingerprint checks — plus the probe-model sweep, in CI. The tool surface gets the same regression discipline as the code behind it, and smoke-workspace-mcp --check-surface diffs the simulator's surface against the deployed server so the benchmark can never quietly measure an API that no longer exists.

That last property is what Part 3 depends on. Once the surface is stable and its failure classes are being fixed deliberately, every graded episode becomes an artifact with a shelf life — 1,800 of them are already committed to the repo. Part 3 turns them into training data.
