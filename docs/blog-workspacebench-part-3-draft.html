Turning eval traces into a learning interface

July 2026 · Part 3 of 3 · WorkspaceBench · Part 1 · Part 2

Part 1 measured whether agents can operate OpenBB Workspace. Part 2 used those measurements to fix the MCP tool surface itself. This post starts after both, and the ordering is the whole point: traces collected against a tool surface you are still changing describe an API that no longer exists. With a stable surface, every run's trace — what the agent saw, what it tried, what the workspace returned, how the final state was graded — becomes data worth keeping.

And we are not speculating about hypothetical data. The calibration sweep left behind 1,800 fully graded episodes — six models × 300 scenarios, committed to the repo as portable rollout JSONL. This post is about what that corpus is for.

One trace, three uses

A score tells you whether an agent passed. A trace tells you why — the task, the observations, the tool calls, the results, the final workspace, the grade. WorkspaceBench normalizes every attempt into one canonical rollout record, and that one record serves three consumers with a single verifier behind all of them:

Anatomy of a real episode

Here is an actual record from the committed corpus: Qwen3 8B on gen_t2_read_var_trend — read a risk widget's data and write a note citing values from it. The episode is verbatim from runs/exports/v1-calib-qwen3-8b-rollouts.jsonl.

Every rollout record carries the same envelope: task, messages, tool_calls, tool_results, final_snapshot, grade, and versioning metadata — scenario id, pack release, model slug, export schema version, timestamp. A training row can always be traced back to the exact benchmark release that produced it. If you cannot audit the data, you cannot trust the training run.

The corpus we already have

The export paths are commands, not aspirations:

# lossless per-attempt records from a finished comparison run
workspace-bench export-rollouts --comparison-dir runs/comparison/<run> --output rollouts.jsonl

# supervised examples from passing attempts (or oracle reference traces)
workspace-bench export-sft --comparison-dir runs/comparison/<run> \
  --format openai_messages --output sft.jsonl

# chosen/rejected pairs from repeated attempts on the same scenario
workspace-bench export-preferences --comparison-dir runs/comparison/<run> --output prefs.jsonl

SFT export drops failed attempts unless you opt in with --include-failures, and then the grade metadata rides along. The benchmark decides what happened before any training pipeline consumes the trace.

Where the learning signal lives

Learning signal comes from contrast. If every attempt passes, there is nothing to prefer; if every attempt fails, there is nothing to reinforce. The calibration corpus gives contrast two ways:

Across models, today. The 192 contested scenarios pair a passing trace against a failing trace on the identical task — GPT-5.5's clean solve of a layout composition against Qwen3 8B's truncated attempt is a preference pair with a verifiable label. That is what single-attempt runs across six models buy you.

Within one model, shortly. Same-model variance needs repeats. That run is in flight: the gating model × 3 attempts × all 300 scenarios, 900 graded episodes.

The distillation target is visible in the curves

Part 1's sharpest small-model finding: Qwen3 8B doesn't degrade with tier, it breaks — near mid-field parity at t0–t1 (80%, 78%), then 47% at t2 and 17% at t4. The model has the tool syntax; what it lacks is episode-level planning across multi-step compositions. That is precisely the gap trace-SFT targets, and the corpus contains the teacher material: over a thousand passing frontier traces, concentrated in the tiers where the 8B fails.

The experiment writes itself: SFT Qwen3 8B on frontier passing traces from the train split (180 scenarios), evaluate strict pass on the validation split (60), report the t2–t4 delta. The before-numbers are already published in Part 1; the after-numbers get a panel here when the run lands.

Difficulty was earned, not labeled

An earlier draft of this post proposed empirical difficulty gating as a discipline worth adopting. Between drafts, we did it — Part 1's calibration is exactly that protocol executed: a named gating model over all 300 scenarios, a required monotonic pass-rate curve as the acceptance test, and three real benchmark defects caught and fixed before any number was published. The gating curve — 98 → 92 → 77 → 52 → 33 — is now the operational definition of the tiers.

What remains open, honestly: banding with repeats (the 900-attempt run above upgrades tier membership from point estimates to bands), and a t5 built from the 15 all-fail scenarios rather than from more composition — Part 1's frontier results show composition is not where the remaining difficulty lives.

Split discipline before training

The release ships 180/60/60 train/validation/test, stratified per family×tier cell — every slice of the distribution appears in every split. For evaluation that is exactly right. For training, one honest caveat carries over from Part 1: stratification means the same template family spans splits with different parameters, so a model trained on the train split could learn family-shaped shortcuts. Before trusting a training result, prefer held-out-family splits — hold entire families out of training and measure on them. The schema supports it; it is queued as the first change training work forces on the benchmark.

The same task as reset and step

Once the eval loop is deterministic, a scenario can be exposed as a step-based environment. WorkspaceGymEnv wraps WorkspaceEpisode — the same episode object the eval runner uses — so the same scenario, simulator, trace, and grader serve a policy loop. There is no RL-only environment logic to drift out of sync, and reward is the grader, so reward and eval score cannot disagree by construction. 

from workspace_bench.core.runner import find_scenario
from workspace_bench.rl.env import WorkspaceGymEnv

env = WorkspaceGymEnv(scenario=find_scenario("gen_t2_read_var_trend"))
observation, info = env.reset(seed=1)
observation, reward, terminated, truncated, info = env.step(
    {"tool": "get_workspace_snapshot", "args": {}}
)

The default reward is sparse final-state correctness. Process shaping — schema-before-create, valid identifiers, no repeated snapshots — is available as opt-in additive reward reusing the trace checks, and it is opt-in for a reason. I have written before about what happens when you reward the thing you can measure instead of the thing you want; a workspace agent that learns to farm discovery-discipline bonuses without shipping dashboards would be that post all over again. Sparse first. Shape only what you have verified the sparse reward under-teaches.

Where this goes

The earlier drafts of this series ended by proposing a "task factory" as future work. It quietly stopped being future work: the generator, the certification gates, and the calibration loop from Part 1 are the factory — 300 tasks generated along structured axes, every one certified (oracle passes, no-op fails), difficulty earned against a named gating model. What the factory does not yet do is the next arc: held-out families for honest training splits, a t5 grown from the 15 tasks nobody passes, LLM-in-the-loop synthesis for scenario diversity beyond templates, and a browser-backed runner so the same contract grades agents against the real Workspace instead of its simulator.

The through-line of the series, one last time: measure first, fix the surface second, train third — and let one grader be the arbiter of all three. Incentives always win. The least I can do is measure the ones I am creating, before I start optimizing against them.
