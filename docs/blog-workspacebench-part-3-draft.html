Part 3

Turning eval traces into a learning interface

Part 1 measured whether an agent can operate OpenBB Workspace. Part 2 used those measurements to fix the MCP tool surface itself. Part 3 starts after both: with a stable interface, every run's trace — what the agent saw, what it tried, what the workspace returned, how the final state was graded — becomes data worth keeping. The order matters: traces collected against a tool surface you are still changing describe an API that no longer exists.

Why this matters

The score is useful. The trace is reusable.

A score tells me whether an agent passed. A trace tells me why. It shows the task, the observations, the tool calls, the tool results, the final workspace, and the grade. That is much more valuable than a single number.

In OpenBB terms, this means a run can show whether the agent listed available widgets, inspected the schema, created the right dashboard artifact, recovered from a bad state, or stopped too early. The trace is the evidence.

This is where the benchmark becomes more than a scoreboard. If the trace is clean enough, it can become a supervised example, a preference pair, or an episode inside a step-based environment. WorkspaceBench normalizes every attempt — oracle replays, comparison runs, external agent commands — into one canonical rollout record.

Data exports

Before you train anything, export clean data.

The first useful path is offline. Take passing traces and turn them into supervised examples. Take repeated attempts and turn them into preference pairs. Keep failed attempts only when the grade metadata travels with them.

This is not glamorous, but it is where most of the leverage is. Every exported row carries versioning metadata — benchmark release id, scenario pack, export schema version, model slug, timestamp — so a training row can always be traced back to the exact benchmark release that produced it. If you cannot audit the data, you cannot trust the training run.

Practical rule: export only after grading. The benchmark decides what happened before any training pipeline consumes the trace. SFT export drops failed attempts by default; you have to opt in with --include-failures to keep them, and then the grade rides along.

Supervised fine-tuning

SFT starts from traces that already passed, or from oracle traces that describe the intended behavior. Formats: openai_messages, sharegpt, or raw tool-call JSONL.

# bootstrap from oracle reference traces
workspace-bench export-sft \
  --oracle \
  --format openai_messages \
  --output runs/exports/oracle-sft.jsonl

# or from passing model attempts
workspace-bench export-sft \
  --comparison-dir runs/comparison/<run-id> \
  --format openai_messages \
  --output runs/exports/model-sft.jsonl

Preference pairs

Repeated attempts on the same scenario produce chosen/rejected examples: the passing or higher-scoring attempt is chosen, the failing or lower-scoring attempt rejected.

workspace-bench compare-models \
  --pack all \
  --difficulty all \
  --repeats 3 \
  --metric pass-at-k

workspace-bench export-preferences \
  --comparison-dir runs/comparison/<run-id> \
  --output runs/exports/preferences.jsonl

The real asset

The trace is reusable. The task distribution is the asset.

Here is the thing recent agent-training work keeps converging on: the scarce resource is not the RL algorithm. It is a large, diverse, executable, verifiable task distribution with calibrated difficulty. A clean trace from a bad task distribution is still bad training data.

The clearest way to see this is reward variance. Learning signal comes from tasks a model sometimes solves. If every attempt passes, there is nothing to prefer between attempts. If every attempt fails, there is nothing to reinforce. The useful scenarios are the ones in between — and you only find them by running repeats and measuring.

Difficulty should be measured, not labeled.

Scenarios currently carry author-assigned labels: easy, medium, hard. That is fine for a hand-written alpha pack, but it does not scale. The discipline I want to adopt — borrowed from recent synthetic-environment work like TMax and General Agent — is empirical gating: a task earns its difficulty tier by landing in a target pass-rate band for a named gating model, measured over repeated attempts.

Target pass-rate bands per tier Click a tier

How gating works

Generate or author a candidate scenario. Validate the schema. Assert the no-op agent fails it and the oracle trace passes it. Then run a gating model for N attempts: the task is accepted into a tier only if its measured pass rate lands in that tier's band. Difficulty becomes a property you can version and reproduce, tied to a named solver.

Split discipline comes before training. Today every bundled scenario sits in the dev split — honest for an alpha. Before any training run: train for generated tasks intended for SFT/RL, dev for debugging agents, validation for iteration, test for reporting, hidden for leaderboards. And split by workflow family, not just by scenario — if earnings-prep tier-0 is in train and earnings-prep tier-4 is in test, the model can learn family shortcuts. The schema already supports splits per scenario and per task pack; the discipline is the missing piece, and it is deliberate work, not a flag.

Environment interface

The same task can become reset, step, reward.

Once the eval loop is deterministic, the same scenario can be exposed as a step-based environment. The agent receives an observation, emits a structured action, gets a tool result back, and eventually receives a final grade as reward.

This is where WorkspaceGymEnv fits. It does not replace the benchmark. It wraps WorkspaceEpisode — the same episode object the eval runner uses — so the same scenario, simulator, trace, and grader serve a policy loop. There is no separate RL-only environment logic to drift out of sync.

Minimal loop

A policy loop only needs reset, step, and a structured action. The return shape is Gymnasium's, but Gymnasium is not a dependency.

from workspace_bench.core.runner import find_scenario
from workspace_bench.rl.env import WorkspaceGymEnv

scenario = find_scenario("l1_add_price_widget")
env = WorkspaceGymEnv(scenario=scenario)

observation, info = env.reset(seed=1)
observation, reward, terminated, truncated, info = env.step({
    "tool": "get_workspace_snapshot",
    "args": {},
})

The v1 contract

The first version has a clear boundary.

I do not want this to be vague. For v1, the goal is a clean interface: agents can be measured, traces can be exported, and policies can interact with the same tasks through a stable environment API. Everything downstream inherits from one source of truth.

Deterministic workspace state

Fixture-backed scenarios make local evals repeatable and suitable for regression tests, CI, and rollouts. No live market data by default.

One grader contract

Normal runs, exports, and environment rollouts all use the same final-state grading. Reward and score can never disagree.

Private task-pack path

Teams point the same scenario schema at internal backends and keep graders local. BYO data without forking the harness.

Split metadata

Scenarios and task packs carry dev, validation, test, or train splits so training and reporting data can be separated cleanly.

Explicit export formats

Rollouts, SFT records, and preference pairs are produced only through export commands. Publishing a benchmark never silently publishes training data.

Environment wrapper

WorkspaceGymEnv wraps the benchmark episode without duplicating scenario or grader logic. Sparse final reward by default; process rewards opt-in.

The point: the benchmark remains the source of truth. Data exports and environment rollouts are downstream views of the same evaluated behavior.

Where this goes next

Hand-written evals are the seed, not the destination.

Forty polished scenarios are a benchmark. They are not yet an environment. The serious unlock — the direction TMax's 14,600 terminal environments and General Agent's 4,500 evolved tasks both point at — is a task factory: a pipeline that generates Workspace scenarios along structured axes, evolves them across difficulty tiers, and certifies each one before it ships.

Certification is the part that keeps generation honest. Every candidate task must fail with no actions, pass under its reference trace, and land in its tier's pass-rate band for a gating model. Generation without verification just produces benchmark-shaped noise.

The factory loop Click a stage

Synthesize

Generate candidate scenarios from task-family templates along explicit axes: workflow, persona, capability, artifact target, data topology, initial-state pathology, constraint type, layout rigor, ambiguity. The axes describe the distribution's shape — not just "40 scenarios" but what they cover.

That is Part 4 territory: from eval suite to environment factory. The order across this series is deliberate — benchmark first, tool surface second, training data third, environment factory fourth. Everything downstream consumes the same certified asset.
